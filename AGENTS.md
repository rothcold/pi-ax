# pi-ax

Independent Pi extension: host Pi orchestrates one-shot Pi workers in real Google AX sandboxes.

Original code is MIT-licensed under root `LICENSE`; preserve the Apache-2.0 vendored proto license/headers and wire/image provenance. `npm run check:package` checks release metadata, entrypoints, MIT/third-party licenses and runtime-config exclusion in the tarball. Release preparation for public `pi-ax@0.1.0` is authorized and the private flag is removed; publication remains a separate owner action. Keep the official `*` host peers and exact tooling shrinkwrap. The worker recipe copies the project MIT license alongside third-party notices; this recipe change is not a new image build/runtime acceptance. Root `/ax-config.json` is ignored; never commit personal/runtime configuration.

First-version implementation is authorized; real AX runtime acceptance remains required. Upstream authentication, network isolation and resource-enforcement deficiencies are deferred documented limitations, not blockers or new deliverables. `implementation.md` is a historical architecture draft, not an authoritative approved contract. Before AX integration design or implementation, read `docs/ax-verification.md` for pinned-source findings, gaps and runtime validation requirements.

Use `npm ci` and `npm run check` (lint, typecheck, Node tests); individual `npm run lint`, `npm run typecheck`, and `npm test` are available. `npm run generate:proto` regenerates pinned wire types. Transport tests use an in-process gRPC server, not real AX E2E. README.md describes installation/configuration and current verification. Root `npm-shrinkwrap.json` is the exact tooling lock and ships in tarballs. Worker Pi uses `latest` with no project lock: `npm run build:image` freshly resolves npm latest, fails on lookup errors, and passes the resolved version into Docker's install cache input. It verifies/records the installed version in the build log, image label `org.pi-ax.pi.version` and `/opt/pi/pi-version`. Rebuild/deploy/select a new digest to upgrade; no running-task or host Pi auto-upgrade. Do not run worker `npm ci` or reintroduce worker lockfiles. Future latest compatibility requires validation.

Worker/snapshot protocol, image build and limits are documented in `worker/README.md`; `npm run build:worker` compiles the one-shot wrapper and Linux C subreaper (`cc` required locally). The inspected Pi bash implementation detaches process groups: never equate wrapper exit with whole-job termination. Correlated `termination.json` proof is required before releasing the active slot or confirming cancellation; missing proof stays unknown. Actual Pi bash supervision tests identify the installed root-tooling Pi (currently 0.99.2), not the floating image; they are still not model/AX E2E. Worker subprocess fixtures and local Git patch round trips are tests, not real Pi/AX SQLite acceptance. Preserve this distinction and the pinned upstream provenance when changing worker assets.

Host tool/lifecycle contracts and recovery are documented in `docs/lifecycle.md`; the Pi entrypoint is `src/extension.ts`. Default task state lives outside source trees in `~/.pi-ax` (or explicit `stateDir` in `ax-config.json`), with Linux util-linux `flock` enforcing one active reservation across local processes. Never infer remote cancellation from transport abort, replay an uncertain start, or delete unexported results without explicit destructive intent. Lifecycle fake-transport tests and local process-lock tests are not real AX acceptance.

Integration scripts and setup are in `docs/local-ax.md`; actual passed/blocked/not-run evidence is in `docs/v1-validation.md`. `npm run check:package` tests the extracted tarball with the actual Pi loader and existing lock-verified dependencies, no model call; it is not a fresh consumer install. Release preparation separately passed isolated local-tarball npm installs and actual five-tool/schema loader probes on host Pi 0.99.2 and 1.2.0. That is host-only evidence, not an npm-registry install or worker/AX acceptance. `npm run build:image` builds the real pinned AX-runner image with build-time latest Pi. Root tooling, AX-source and Node pins remain separate; historical 0.99.2 image/guest evidence is not acceptance of newer Pi. `npm run local:ax -- prepare|create|deploy|cleanup` is opt-in real infrastructure, uses ignored `.cache/pi-ax`, unique names/private kubeconfig, and never invokes upstream's destructive cluster recreation script. `npm run e2e:wire` is not a model test; `npm run e2e:sqlite` requires explicit model credentials and fresh external evidence storage. Never promote image/build/control-plane success to guest/Pi SQLite acceptance. The corrected route passed actual AX/gVisor wire and detached-Pi-bash supervision probes. One real `minimax/MiniMax-M3` SQLite run passed on 2026-10-15 with the image recorded in `docs/v1-validation.md`, including source/database export, termination proof and four-resource cleanup. Preserve that image-scoped evidence, earlier activation/golden-snapshot/model failures, and untested recovery cases; do not claim future latest images are accepted.

Runtime settings come only from `getAgentDir()/ax-config.json`, default `~/.pi/agent/ax-config.json`, respecting Pi's `PI_CODING_AGENT_DIR` expansion. `src/config.ts` defines the strict TypeBox schema; `ax-config.example.json` ships non-secret placeholders. No legacy PI_AX runtime environment fallback. `credentialEnv` lists names only; the shared host/worker policy in `src/credentials.ts` reads values only during execution. Extension registration stays lazy, and retained-task management validates storage selection independently of current spawn/model settings. Keep v1 task record shape and default state location unchanged. Test with isolated HOME/agent directories, never personal configuration/auth. Separate `PI_AX_LOCAL_*` deployment knobs and explicit cleanup confirmation remain unchanged.
